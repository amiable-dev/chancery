# Read-Only Security Scanning

## Definition
Read-Only Security Scanning is a design principle for security tools that restricts the scanner to passively reading on-disk metadata and structured data files — never invoking package managers, executing install scripts, lifecycle hooks, or any code from the artefacts under inspection — specifically to avoid triggering the class of attack the scanner is designed to detect.

## Explanation
The danger is subtle but significant: a naive supply-chain scanner might call `npm ls`, `pip show`, or `gem list` to enumerate installed packages. For any package with a malicious `postinstall` or `post_install` hook, that invocation executes the attack payload. The scanner becomes the attack vector.

This is not hypothetical. npm's `postinstall` scripts run automatically on `npm install` — and sophisticated supply-chain packages use this to execute their payload on first install. A scanner that calls `npm` to discover packages can re-trigger those hooks. The same applies to pip's `entry_points`, RubyGems `post_install_message` hooks, and Composer scripts.

**What read-only scanning avoids invoking:**
- `npm`, `pnpm`, `yarn`, `bun` (and any `node_modules/.bin/` scripts)
- `pip`, `pip3`, `pipx`, `uv`
- `gem`, `bundle`
- `go build`, `go run`
- `composer`
- Any script found inside `package.json` `scripts` fields
- Any executable in a package's directory

**What it reads instead:**

| Source | Read instead of... |
|---|---|
| `package-lock.json` | `npm ls --json` |
| `*.dist-info/METADATA` | `pip show <pkg>` |
| `go.sum` / `go.mod` | `go list -m all` |
| `Gemfile.lock` | `gem list` |
| `composer.lock` | `composer show` |
| VS Code extension `package.json` | `code --list-extensions` |

This approach is robust: lockfiles and metadata files are generated by the package manager at install time and reflect the actual installed state. They are canonical, parseable, and do not require invoking any binary to read.

**Confidence implications:**

Reading metadata directly means some version information may be partial or inferred. Bumblebee addresses this by tagging each record with a confidence level:
- **High** — exact identity and version from canonical metadata (e.g., `*.dist-info/METADATA` for PyPI)
- **Medium** — identity is reliable but version or source is partially inferred
- **Low** — only a config path or dependency spec was found (e.g., a package name in an MCP config without an installed version)

This transparency prevents false positives from being acted on and helps responders triage correctly.

**The broader principle:**

Read-only scanning embodies a security principle analogous to "don't run untrusted code": when auditing a system for compromise, the auditing tool must not trust the system it's auditing. Invoking system commands grants trust to the package ecosystem's execution model. Reading files doesn't.

This principle extends beyond supply-chain scanning. Any forensic or security tool that targets a potentially-compromised environment should minimise its trust surface: prefer file reads to process invocation, prefer structured data parsing to shell pipelines, prefer static analysis to dynamic evaluation.

## Key Properties
- **Non-triggering** — avoids executing any code from the scanned artefacts
- **Lockfile-first** — parses the same structured data the package manager writes, not re-derived data
- **Confidence-aware** — explicitly models uncertainty when metadata is partial
- **Forensics-compatible** — appropriate for scanning potentially-compromised environments where running installed binaries would compound the compromise
- **Zero side-effects** — does not modify any file, database, or state; suitable for automated fleet scanning without approval gates per machine

## Relationships
- Enables [[developer-endpoint-inventory]]: the inventory is only safe and correct because it uses read-only methods
- Contrasts with EDR agents: EDR hooks into process execution (a write/intercept model), whereas read-only scanning only observes filesystem state
- Related to [[constrained-agent-actions]]: both are about minimising the action surface of a tool operating in a potentially-hostile environment
- Related to [[offensive-defensive-symmetry]]: understanding how attacks execute (via install hooks) informs why a defensive tool must not invoke those same execution paths

## Applications
- **Supply-chain incident response:** When a malicious npm package is reported, scan 500 developer laptops via fleet tooling without risk of re-triggering the payload on any machine that has it installed.
- **Continuous compliance scanning:** Schedule weekly scans that run silently in the background — no user prompts, no package manager invocations that could disrupt running dev environments.
- **Air-gapped or sensitive environments:** In environments where execution of untrusted code is strictly controlled, read-only scanning can proceed without requiring code-execution approval.
- **Tooling design principle:** When building any security tool that targets developer machines, apply this principle: parse manifests, lockfiles, and metadata; never invoke the ecosystem's CLI.
