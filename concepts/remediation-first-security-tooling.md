# Remediation-First Security Tooling

## Definition
Remediation-first security tooling is a design philosophy for vulnerability scanners and security tools where the primary output for each finding is a validated, actionable fix — a concrete command or change the developer can execute immediately — rather than just an advisory identifier (CVE ID, GHSA number) or a severity score. The scanner's job is not to inform; it is to unblock.

## Explanation
The dominant paradigm in security tooling has historically been detection-and-report: find the vulnerability, report its identifier and severity, and leave remediation to the developer. This produces two failure modes:

1. **Alert fatigue:** Developers receive lists of CVE IDs with severity scores but no clear action. After the third sprint of "investigate GHSA-xxxx" leading to hours of research with no obvious fix, engineers deprioritise security tickets.

2. **Research overhead:** A CVE ID tells you *what* is vulnerable. It doesn't tell you *how your specific project should fix it*, given your particular package manager, your specific version constraint, and your current lockfile state. That derivation falls on the developer.

Remediation-first tools invert this. The OWASP CVE Lite CLI output for a finding is not:
```
CRITICAL: jsonwebtoken@0.1.0 — GHSA-27h2-hvpr-p74q
```
It is:
```
CRITICAL: jsonwebtoken@0.1.0 — GHSA-27h2-hvpr-p74q
  Type: TRANSITIVE (via express-jwt@0.1.3)
  Fix: npm update express-jwt
  Confidence: HIGH (semver resolution confirmed — fixes within ^0.1.x range)
```

The developer can copy the fix command and run it. No research required.

**What "validated" means:**
The fix command is not generated by template substitution. The tool actually resolves the fix: it checks whether the parent package's semver constraint allows a version that includes the fix, simulates the resolution, and confirms the vulnerable package would be replaced. If the semver range doesn't allow a fix, the tool escalates to a major upgrade recommendation or flags it as "no fix available."

**The auto-fix extension:**
Taking this philosophy to its logical conclusion, `--fix` mode applies the fix automatically: run the package manager update, then immediately rescan to confirm the vulnerability is resolved. The developer reviews a diff rather than running commands. This is the security equivalent of `prettier --write` vs `prettier --check`.

**Design principles of remediation-first tools:**
1. **Every finding has a recommended action.** "No fix available" is a valid state — communicate it explicitly, not by omission.
2. **Actions are package-manager-native.** The command for npm is `npm update x`; for pnpm it's `pnpm update x`. Not a generic instruction to "upgrade the package."
3. **Confidence levels are explicit.** "Confident fix" vs "breaking change required" vs "no fix available yet" are different states with different developer responses.
4. **Output is structured for both humans and machines.** Copy-paste for the developer; SARIF/JSON for CI pipelines.
5. **Developer workflow timing:** Run immediately before push, not as a delayed CI artifact — catch issues when context is fresh.

**Alert fatigue connection:**
Remediation-first design is the technical answer to [[approval-fatigue]] in security. When every alert comes with a fix, the cost of acting on an alert drops to near zero. When the cost is near zero, developers act. Alert fatigue is caused not by too many alerts, but by too many alerts with no clear path forward.

## Key Properties
- Output-oriented: the primary user artifact is a fix command, not an advisory reference
- Package-manager-native: fix commands are scoped to the detected package manager (npm/pnpm/yarn/bun)
- Validated: fix resolution is computed, not templated — confirms the fix actually works in the current dependency graph
- CI-compatible: structured output (SARIF, JSON) enables the same data to feed automated gating
- Timeliness-focused: designed for pre-commit/pre-push use, not post-merge dashboards

## Relationships
- Addresses [[approval-fatigue]]: when every finding includes a validated fix, the barrier to acting is low enough that developers engage
- Depends on [[direct-vs-transitive-vulnerability]]: fix command generation requires knowing the dependency chain to prescribe the right parent update
- Outputs to [[sarif-format]]: the fix metadata can be expressed in SARIF `fix` objects for consumption by CI/CD platforms
- Related to [[reachability-aware-vulnerability-scanning]]: remediation is most valuable when scoped to reachable vulnerabilities — fixing a package that isn't imported isn't worth the risk of a breaking change

## Applications
- **Pre-commit hooks:** `cve-lite . --fail-on high` blocks commits that introduce critical vulnerabilities — with immediate fix guidance so the block isn't a dead end
- **Onboarding scans:** Run on a new project checkout; the output is a to-do list with associated commands, not a research task
- **Security sprint planning:** Generate remediation-first reports; each finding maps to a Jira ticket with a one-line resolution
- **Dependency update automation:** Combine remediation-first output with Renovate/Dependabot for automatic PR generation with pre-validated fix commands
- **Security oncall runbooks:** When a new critical advisory drops, the runbook step is "run `cve-lite . --fail-on critical`" — the fix command is in the output
