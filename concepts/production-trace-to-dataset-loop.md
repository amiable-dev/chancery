# Production Trace-to-Dataset Loop

## Definition
An LLMOps design pattern in which real production traces (actual conversations, agent runs, or tool-call sequences generated by live users) are promoted directly into offline evaluation datasets — closing the loop between "what happened in production" and "what we test against before shipping the next change." The pattern depends on a specific infrastructure choice: co-locating development and production data in the *same* workspace/store, rather than partitioning by environment.

## Explanation
Offline evaluation is only as good as its test set. Hand-curated test sets go stale — they reflect what engineers imagined users would ask, not what users actually ask. The trace-to-dataset loop solves this by making real production usage the primary source of new eval examples.

**The mechanism, concretely (Schneider Electric / LangSmith implementation):**

1. A product's LangSmith workspace spans **all environments** (dev, QA, pre-prod, prod) rather than having one workspace per environment.
2. Every production conversation is traced into that shared workspace.
3. A Subject Matter Expert (SME) — someone with domain knowledge but not necessarily engineering skill — reviews a production trace via an **annotation queue** and marks it as correct, incorrect, or edits the ideal response.
4. The annotated trace is pushed directly into a **dataset** that lives in the same workspace.
5. That dataset is replayed against the next candidate version of the agent (new prompt, new model, new tool config) as part of the offline evaluation suite.
6. If the new version regresses on real production examples, it doesn't ship.

**The critical architectural decision this depends on:**
The alternative design — one workspace *per environment* — seems like the "safer," more conventional isolation choice (separate dev/staging/prod, standard software engineering hygiene). But it silently breaks this loop: if production traces live in a separate workspace from the dev datasets, promoting a trace into a dataset requires a manual export/import step across a workspace boundary, which in practice doesn't happen at scale. Schneider explicitly names this as the reason they chose one-workspace-per-product over one-workspace-per-environment — the loop only works if traces and datasets are co-located.

**Downstream effects of the loop being closed:**
- **Regression datasets stay current.** As user behaviour shifts, the dataset shifts with it, because new production traces keep flowing in — no separate "someone should update the golden set" chore.
- **Drift detection becomes cheap.** Because traces are continuously captured in the same place evaluation happens, comparing this month's production trace distribution to last month's is a query, not a project.
- **SME effort compounds.** Every annotation an SME makes has permanent value — it becomes a reusable regression test, not a one-off judgment that evaporates after the ticket closes.

**Production example (Schneider's "One Jo" assistant):** 160,000 employees across 107 countries generate conversation traces continuously. Those traces feed regression datasets used to validate every new model/prompt iteration, and simultaneously provide drift-detection signal — the same trace stream serves both evaluation and monitoring purposes.

## Key Properties
- **Requires co-located storage** — the loop physically cannot close if production traces and dev/eval datasets live in isolated stores; environment-per-workspace partitioning is an anti-pattern for this reason
- **Human-mediated promotion** — an SME (or engineer) annotation step sits between "trace exists" and "trace becomes a dataset example"; raw unreviewed traces are not directly usable as eval ground truth
- **Bidirectional value** — the same trace stream simultaneously feeds drift/regression monitoring (observability) and test-set curation (evaluation) — one signal, two consumers
- **Self-reinforcing over time** — dataset quality compounds as more real traffic flows through the annotation queue, unlike static hand-written test sets which decay in relevance
- **Domain-expert accessible** — the annotation queue is deliberately scoped as a role with dataset/annotation access but no developer-level surface, so non-engineers can contribute directly

## Relationships
- Depends on [[llm-observability]]: the loop cannot exist without trace-level observability capturing every production interaction in the first place
- Feeds [[genai-eval-envelope]]: promoted production traces become concrete examples used to check whether new outputs fall inside the acceptable-output envelope
- Implements [[human-in-the-loop-pattern]] at the dataset-curation layer: SME annotation queues are a HITL checkpoint whose output is a dataset row rather than an approval/rejection of a single action
- Contributes to [[llmops-maturity-framework]]: "is user feedback flowing back and reused" — one of the core maturity checklist dimensions — is precisely this loop being operational
- Is the LLMOps-specific instance of [[external-feedback-loop]]: real user interactions (traces) inform what the team tests against next, mirroring how external feedback informs the next product iteration
- Contrasts with [[sandbox-per-session-isolation]]: sandbox-per-session deliberately prevents any state from crossing session boundaries (security goal); the trace-to-dataset loop deliberately promotes state across the prod/dev boundary (evaluation goal) — same "isolation vs. sharing" tension, opposite resolution because the goals differ (security containment vs. eval-set freshness)

## Applications
- **Regression suite maintenance without manual curation:** New production traffic patterns automatically become eligible test cases once annotated, instead of requiring engineers to hand-write new test cases as usage evolves
- **Drift detection:** Compare current production trace characteristics (topics, failure modes, latency) against the historical trace distribution already captured in the same store
- **SME-driven quality improvement:** Domain experts without engineering access can directly shape what "correct" means for the next model version by annotating traces they encounter in normal review work
- **Workspace/store architecture decisions:** When designing any LLM observability + evaluation setup (LangSmith, Langfuse, or homegrown), this pattern argues explicitly against per-environment data partitioning if trace promotion is a goal
- **Homelab-scale analogue:** The Council Critique-Shadowing task (`prompts.jsonl` growing from real Council failures) is a lightweight version of this exact pattern — real failures become future eval examples, at a much smaller scale than Schneider's
